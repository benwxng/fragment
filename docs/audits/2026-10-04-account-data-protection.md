# Glance account and data protection audit

Audit date: October 4, 2026 (America/New_York). Scope: current working tree, current production Neon configuration, read-only production database checks, and isolated local tests. Existing uncommitted work was preserved. No product code, deployed settings, users, email, or production data was changed.

## Answer to the launch question

**The architecture supports installing the extension, creating an account, and saving a private account library. It is not yet a fully verified public-launch flow.** The current implementation uses Neon Managed Auth, a Neon Function API, Postgres row-level security (RLS), and private object storage. Supabase files are historical migration/fallback material.

A new user can inspect without an account. Saving initiates website sign-in through Chrome's identity window. Email/password signup and email-code verification are implemented; Google is also offered. After verification and explicit extension approval, the extension receives a separate revocable session. A successful save uploads the screenshot and inserts an owner-scoped capture. Both library surfaces read the same account data.

The strongest confirmed evidence is that production has the expected private bucket and owner RLS, the deployed API rejects anonymous access, and local auth/storage tests pass. Remaining launch gates are production email/OAuth configuration, an actual fresh-user inbox/consent/extension test, and current release integration tests. An account's data is protected from other ordinary users by authorization and database policies; this is not end-to-end encryption that hides data from the service operator.

**Saving currently requires an account and a working connection.** There is no durable offline save queue for new users. Images and already-loaded references may remain in memory during a temporary outage, but a fresh/reloaded offline library cannot be relied upon. The only IndexedDB code is recovery of older installations; it explicitly never creates a local library for new users ([legacy.ts:10](</Users/ben/Documents/font extractor/apps/extension/src/storage/legacy.ts:10>)). The obsolete retry alarm is cleared ([background.ts:121](</Users/ben/Documents/font extractor/apps/extension/entrypoints/background.ts:121>)). A failed inspector save offers retry while the page/target is available; it has not durably saved the capture.

The screenshot is written before the capture row. An interrupted/failed metadata write can leave an unreferenced private image. Add orphan cleanup and storage quotas before broad growth; do not imply atomic database-plus-object-storage transactions ([data.ts:23](</Users/ben/Documents/font extractor/packages/capture/src/library/data.ts:23>), [api.ts:137](</Users/ben/Documents/font extractor/backend/api.ts:137>)).

## Protection that is implemented

- **Verified identity:** Web requests verify EdDSA signature, issuer, audience, and expiry using Neon JWKS. Both extension and web identities check verification and bans against current user records. Imported libraries are claimable only by a verified matching email ([auth.ts:15](</Users/ben/Documents/font extractor/backend/auth.ts:15>), [auth.ts:25](</Users/ben/Documents/font extractor/backend/auth.ts:25>), [auth.ts:55](</Users/ben/Documents/font extractor/backend/auth.ts:55>)).
- **Per-account database protection:** `asOwner()` wraps each capture operation in a transaction, switches to `refer_app`, and sets transaction-local owner identity. RLS has both `USING` and `WITH CHECK`; composite foreign keys prevent assigning another user's collection/tag ([db.ts:7](</Users/ben/Documents/font extractor/backend/db.ts:7>), [001_refer.sql:76](</Users/ben/Documents/font extractor/neon/migrations/001_refer.sql:76>), [001_refer.sql:174](</Users/ben/Documents/font extractor/neon/migrations/001_refer.sql:174>)).
- **Private image access:** API constructs keys as account/capture UUIDs; clients cannot provide another account's path. Authenticated image download additionally requires an owned capture row. Legacy capture endpoints issue one-hour signed URLs; anyone holding an unexpired URL can use it, so treat those URLs as credentials ([validation.ts:9](</Users/ben/Documents/font extractor/backend/validation.ts:9>), [api.ts:66](</Users/ben/Documents/font extractor/backend/api.ts:66>), [api.ts:125](</Users/ben/Documents/font extractor/backend/api.ts:125>)).
- **Session handling:** Codes are SHA-256 hashed, bound to PKCE and redirect, consumed transactionally, and expire after two minutes. Extension tokens are random, stored hashed server-side, expire after 30 days, and are removed remotely on successful extension signout. Browser storage contains the extension bearer token, not a database or storage secret ([auth.ts:6](</Users/ben/Documents/font extractor/backend/auth.ts:6>), [api.ts:28](</Users/ben/Documents/font extractor/backend/api.ts:28>), [001_refer.sql:205](</Users/ben/Documents/font extractor/neon/migrations/001_refer.sql:205>), [client.ts:13](</Users/ben/Documents/font extractor/apps/extension/src/cloud/client.ts:13>)).
- **Web transport:** Same-origin library proxy checks mutation origin, checks expected owner before forwarding, sets no-store, restricts allowed paths, and keeps this transport's bearer token on the server. Installed Neon SDK cookies default to HttpOnly, Secure, SameSite=Lax ([route.ts:4](</Users/ben/Documents/font extractor/apps/web/app/api/library/[...path]/route.ts:4>), [server.ts:4](</Users/ben/Documents/font extractor/apps/web/lib/auth/server.ts:4>)).
- **Account switching:** Extension requests pin their starting session; a stale 401 cannot remove a newer token. Shared renderer clears account-specific references on an observed owner change and ignores late responses after a reset. Legacy imports are bound to their original account ([client.ts:113](</Users/ben/Documents/font extractor/apps/extension/src/cloud/client.ts:113>), [index.ts:902](</Users/ben/Documents/font extractor/packages/capture/src/library/index.ts:902>), [legacy.ts:36](</Users/ben/Documents/font extractor/apps/extension/src/storage/legacy.ts:36>)).
- **Capture minimization:** URLs strip credentials/query/fragment; excerpts exclude editable fields and hidden content. The screenshot path temporarily hides normal editable controls before capture. Visible page content may still contain sensitive data; this is not general-purpose redaction ([privacy.ts:7](</Users/ben/Documents/font extractor/packages/capture/src/privacy.ts:7>), [privacy.ts:24](</Users/ben/Documents/font extractor/packages/capture/src/privacy.ts:24>), [bootstrap.ts:61](</Users/ben/Documents/font extractor/apps/extension/src/inspector/bootstrap.ts:61>)).

## Launch gates and important gaps

1. **Configure production authentication.** Replace shared Google credentials with an owned OAuth app and shared SMTP with a production sender, verify delivery, use Glance branding, and move local development to a separate branch before disabling localhost on production. These are called out by Neon's current [production checklist](https://neon.com/docs/auth/production-checklist) and [OAuth setup](https://neon.com/docs/auth/guides/setup-oauth). The production callback origin is already trusted.
2. **Complete an actual fresh-user release test.** Use a packaged/store-installed extension in a clean browser profile, an actual email inbox, code verification, extension approval, capture upload, web/library reload, a second device/profile, deletion, signout, expired sessions, and account switching. Also test Google with a user outside the developer's team. This audit did not create users, send email, grant consent, or write production data.
3. **Update integration tests to the current architecture.** `smoke-neon-extension.mjs` still expects `Connect extension`, `sync-now`, and pending-queue fields ([line 36](</Users/ben/Documents/font extractor/scripts/smoke-neon-extension.mjs:36>)); `verify-library-sync.mjs` expects offline durable caching and the removed sync message ([line 24](</Users/ben/Documents/font extractor/scripts/verify-library-sync.mjs:24>)). `packages/database/tests/migration.test.ts` tests the old Supabase migration ([line 14](</Users/ben/Documents/font extractor/packages/database/tests/migration.test.ts:14>)). Add maintained Neon migration/owner tests and fresh signup/connect tests, and run against an isolated test branch. Historical passes in setup docs are not a current release signoff.
4. **Bind production authorization to the real Glance extension.** `validateRedirect()` accepts every syntactically valid Chromium extension ID and Firefox callback host ([validation.ts:14](</Users/ben/Documents/font extractor/backend/validation.ts:14>)); the approval page labels the requester Glance ([connect/page.tsx:23](</Users/ben/Documents/font extractor/apps/web/app/extension/connect/page.tsx:23>)). PKCE protects the exchange but does not identify the requesting extension as the released Glance client. Allowlist final release IDs/callbacks in production and separate approved development IDs. This is a consent-phishing/trusted-client hardening gap, not evidence of an anonymous account-data bypass.
5. **Finish account recovery and data lifecycle.** The product exposes signup, signin, verification, and signout, but no forgot-password/reset-password, account deletion, or connected-device/session-management UI. Provide a working recovery path and a documented/supportable data-deletion process before taking public accounts. Deleting Neon Auth users also needs coordinated application-account cleanup because the account FK is not cascading ([001_refer.sql:18](</Users/ben/Documents/font extractor/neon/migrations/001_refer.sql:18>)). Confirm backup/restore retention, exercise restoration, and consider protecting the production branch.
6. **Correct product and technical claims.** Architecture/setup docs still describe offline queues and a device-bound local library ([ARCHITECTURE.md:229](</Users/ben/Documents/font extractor/docs/ARCHITECTURE.md:229>), [NEON_SETUP.md:140](</Users/ben/Documents/font extractor/docs/NEON_SETUP.md:140>)). Current code uses account-required online saves and memory-only read reuse. Store copy, privacy disclosures, support docs, and screenshots must match that behavior.

**Verification-setting caution:** Provider `require_email_verification=false` is not an authorization hole in the current backend: unverified identities receive 403 and cannot get extension authorization. Signup currently creates an unverified browser session so `/verify-email` can read the user's email. Simply enabling the provider's require-verification option may stop that session from existing and break this page. Adapt and test the flow before changing that setting ([verify-email/page.tsx:9](</Users/ben/Documents/font extractor/apps/web/app/verify-email/page.tsx:9>)).

**Signout scope:** Web signout ends the web session; extension signout revokes only the current extension token. One does not sign out the other. Extension signout clears the local token even if remote revocation fails; a copied token can remain valid until its 30-day expiry in that case. There is no global revoke-all flow. The verified extension approval page also has no account-switch control; a still-signed-in website can reconnect the same account after extension signout ([actions.ts:21](</Users/ben/Documents/font extractor/apps/web/app/actions.ts:21>), [client.ts:71](</Users/ben/Documents/font extractor/apps/extension/src/cloud/client.ts:71>)).

**Scale and abuse:** Body/image limits exist (2 MiB JSON, 5 MiB images), but this API has no app-level account quota, rate limiter, orphan-object sweeper, or pagination. Every library load returns all captures and downloads uncached images sequentially. Establish storage limits/monitoring and test a large library before a broad launch ([validation.ts:47](</Users/ben/Documents/font extractor/backend/validation.ts:47>), [api.ts:60](</Users/ben/Documents/font extractor/backend/api.ts:60>), [data.ts:74](</Users/ben/Documents/font extractor/packages/capture/src/library/data.ts:74>)).
